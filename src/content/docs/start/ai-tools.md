You can use AI tools when you contribute to Home Assistant, and several repositories ship instructions and skills written specifically for them. This page is the practical side of the [AI policy](/start/ai-policy/): how to get good work out of a tool, and how to stay the person who understands and answers for the result.

An AI tool can save you a lot of reading and typing. It doesn't save you the understanding. Reviewers can tell the difference, and the policy is clear about what happens to pull requests that look like unreviewed AI output: they are closed.

## What the policy asks of you, in practice

The [AI policy](/start/ai-policy/) is short. In daily work, it comes down to this:

- **You understand every change, and can explain it in your own words.** If you can't explain a line, find out what it does or remove it before you open the pull request.
- **You stay in the loop.** Autonomous agents are not allowed. An agent can write code on your machine, but you decide what gets submitted. Don't let a tool open issues or pull requests, or post comments, without you reviewing them first.
- **You answer reviewers yourself.** Using AI to fix your grammar is fine. The substance of your answers must be your own.
- **You disclose honestly where the template asks.** The pull request templates of [Home Assistant Core](https://github.com/home-assistant/core/blob/dev/.github/PULL_REQUEST_TEMPLATE.md) and the [frontend](https://github.com/home-assistant/frontend/blob/dev/.github/PULL_REQUEST_TEMPLATE.md) have two checkboxes: "I understand the code I am submitting and can explain how it works", and "Any generated code has been carefully reviewed for correctness and compliance with project standards". The [Android](https://github.com/home-assistant/android/blob/main/.github/pull_request_template.md) and [iOS](https://github.com/home-assistant/iOS/blob/main/.github/pull_request_template.md) templates ask you to confirm you read the policy, and to select exactly one of three options: no AI, AI assistance, or code fully generated by AI that you reviewed and understood. Leave those parts of the template in place, and tick them only when they are true.
- **You treat AI review comments like any other review comment.** Some projects use AI tools for reviews and triage. They can be wrong. If you think a comment is wrong, say so, briefly.

The agent instructions say the same thing to the tool. In core, the frontend, both apps, [home-assistant.io](https://github.com/home-assistant/home-assistant.io), and the Supervisor, they end with an "AI policy" section that tells the agent not to open issues or pull requests autonomously, and not to post comments for you without your review.

## How the repositories prepare your agent

You don't have to explain Home Assistant to your AI tool from scratch. Most repositories carry two kinds of files for agents:

- **Instructions**: one Markdown file with the basics of the repository, like how to set up the environment, run the tests, and format the code, plus the rules agents keep getting wrong. Most tools read it at the start of every session.
- **Skills**: folders with a `SKILL.md` file each. The front matter has a `name` and a `description`. The tool loads a skill when your task matches its description, or when you ask for it by name. In Claude Code, a skill also becomes a command: the `ha-review` skill runs with `/ha-review`.

Both are plain Markdown, and they are worth reading yourself. The integration skill of core, for example, sums up review guidelines in a few dozen lines.

### Which tool reads which file

Each tool looks in its own places. This is what the official documentation of each tool says:

| File or folder | Read by |
| --- | --- |
| `AGENTS.md` | [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions), and [Claude Code](https://code.claude.com/docs/en/memory) when there is no `CLAUDE.md` |
| `CLAUDE.md` | Claude Code. GitHub Copilot also accepts a `CLAUDE.md` or `GEMINI.md` in the root |
| `.github/copilot-instructions.md` | GitHub Copilot |
| `.github/instructions/*.instructions.md` | GitHub Copilot, for the files that match the `applyTo` pattern of each file |
| `.claude/skills/` | [Claude Code](https://code.claude.com/docs/en/skills) and [GitHub Copilot](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills) |
| `.agents/skills/` | [Codex](https://learn.chatgpt.com/docs/build-skills) and GitHub Copilot |
| `.github/skills/` | GitHub Copilot |

To serve every tool from one source, the repositories use symbolic links. In the frontend, for example, `CLAUDE.md` and `.github/copilot-instructions.md` link to `AGENTS.md`, and `.claude/skills` links to `.agents/skills`. That way, most tools get the same instructions. Not every tool finds every skill folder, though. Codex, for example, reads `.agents/skills/` and not `.claude/skills/`, so in core and home-assistant.io you point it to a skill yourself.

- **[Core](https://github.com/home-assistant/core)**: `AGENTS.md`, with `CLAUDE.md` linked to it. `.github/copilot-instructions.md` is generated from it by `script/gen_copilot_instructions.py`, with extra rules for Copilot code review. Skills in `.claude/skills/`, and a `raise-pull-request` subagent in `.claude/agents/`.
- **[Frontend](https://github.com/home-assistant/frontend)**: `AGENTS.md`, with `CLAUDE.md` and `.github/copilot-instructions.md` linked to it. Skills in `.agents/skills/`.
- **[Android](https://github.com/home-assistant/android)**: `AGENTS.md`, with `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, and `.junie/guidelines.md` linked to it. Skills in `.agents/skills/`, and one in `.github/skills/`.
- **[iOS](https://github.com/home-assistant/iOS)**: `AGENTS.md`, with `CLAUDE.md` and `.github/copilot-instructions.md` linked to it. Skills in `.agents/skills/`.
- **[home-assistant.io](https://github.com/home-assistant/home-assistant.io)**: `.github/copilot-instructions.md`, with `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md` linked to it. Skills in `.claude/skills/`.
- **[Supervisor](https://github.com/home-assistant/supervisor)**: `.github/copilot-instructions.md`, with `AGENTS.md` and `CLAUDE.md` linked to it. No skills.
- **[This site](https://github.com/home-assistant/contributors.home-assistant.io)**: `.github/copilot-instructions.md`, with `AGENTS.md` and `CLAUDE.md` linked to it, and review checklists in `.github/instructions/`. Skills in `.github/skills/`, with `.claude/skills` linked to it.

The [operating-system](https://github.com/home-assistant/operating-system) repository has the AI policy, but no agent instructions or skills.

## Workflows for common tasks

These workflows combine the skills above with the guides on this site. They work with any tool that reads the skill folders. If yours doesn't, point it to the `SKILL.md` file yourself.

### Fix a bug in an integration

1. Reproduce the bug yourself first, and find the issue on GitHub. An agent can't tell you whether its fix fixes *your* bug if you never saw it fail.
2. Ask the agent to find the cause, with the `ha-integration-knowledge` skill. Ask it to write a test that fails because of the bug, before it changes the code. A test that passes without the fix proves nothing.
3. Let it fix the code, then run the tests of the integration yourself, as in [Running the tests](/core/development/testing/): `pytest tests/components/<domain>`. If the fix changes `strings.json`, the core `AGENTS.md` tells the agent to regenerate the English translations first, because the tests read those.
4. Read the diff. Agents like to add more than the fix: extra "defensive" checks, comments that narrate the code, a refactor on the side. Core's instructions tell agents to avoid comments that restate the code and checks that validation already covers, but check anyway, and remove what the fix doesn't need.
5. Open the pull request yourself, with the [template](/core/development/submitting/) filled in. Core has a `raise-pull-request` subagent that runs the checks and fills in the template for you. Know that it pushes your branch and opens the pull request as a draft. It leaves "I understand the code..." and "Any generated code has been carefully reviewed..." unchecked, for you to tick once that is true.

### Build a new integration and take it to Bronze

A new integration must reach the Bronze tier of the [quality scale](/core/quality-scale/), and its first pull request should stay small. Read [Create an integration](/core/integrations/create/) first: it explains when a new integration belongs in core, and sets the limits reviewers ask for.

1. **Start with the library.** The `ha-integration-knowledge` skill says integrations should be thin wrappers, and that protocol and device logic belongs in a separate library on PyPI. An agent happily writes an HTTP client inside your integration. Don't let it. See [Build a Python library](/core/integrations/api-library/).
2. **Generate the skeleton yourself**, with `python3 -m script.scaffold integration`. The scaffold leaves `TODO` comments where your code goes, and a `quality_scale.yaml` with every rule set to `todo`.
3. **Fill it in with the agent, one platform at a time**, with `ha-integration-knowledge` loaded. Ask it to explain the config flow and the coordinator before you move on. You need to explain them later, to a reviewer.
4. **Mark the Bronze rules honestly** in `quality_scale.yaml`: `done`, or `exempt` with a reason. The [rules](/core/quality-scale/rules/) explain each one.
5. **Verify with `ha-quality-scale-verify`.** The skill checks one rule at a time, and every Bronze rule for a tier. It runs tools where they exist, like hassfest, instead of guessing from the code, and marks a rule as unverified when it can't check it. Some Bronze rules are outside the core repository: the `brands` assets, and the `docs-*` rules, which need your documentation pull request on home-assistant.io. Read the report, and fix or exempt what it finds.
6. **Run the checks yourself**: the tests of your integration and `prek run --all-files`. See [Linters, hassfest, and CI](/core/development/checks/).
7. **Read every line**, then open the pull request as above. A reviewer will ask why a piece of code is there. "The AI wrote it" is not an answer the policy accepts.

### Review a pull request

Reviewing helps the whole project, and the core template invites you to review two other pull requests. An AI tool can help you find your way in an unfamiliar change. The review you post must still be yours.

- **Core**: `ha-pr-reviewer` reads the pull request with the GitHub CLI, reviews it with `ha-review`, and checks the open comment threads with `ha-pr-comment-audit`. It reports in your terminal only.
- **Frontend**: `ha-frontend-review`, with the companion skills that match the change. It reads the existing comments first, and gives human feedback priority over feedback from agents.
- **Android**: `ha-android-review`.

Then check each finding against the code before you write it down. Drop the ones you can't confirm or don't understand. Post your review in your own words. Don't paste the tool's output, and don't let the tool post for you. [Reviewing pull requests](/core/development/reviewing/) explains what a good core review looks for.

### Add a card to the frontend

For a new card, the project recommends the Marketplace first, see [share it](/frontend/custom-ui/#share-it). These steps are for a card in the frontend itself.

1. Load `ha-frontend-components` and `ha-frontend-styling`. The components skill lists what a card must do: validate its configuration, handle loading, error, unavailable, and missing entities, and come with an editor when needed.
2. Read `ha-frontend-ux-readiness` before you write much code. A new card is a design decision as much as code. When the direction isn't settled, reviewers ask the design team for input. See [Review and release](/frontend/development/review-and-release/) and [how we design](/design/how-we-design/).
3. Put every visible string through the translation system, as `ha-frontend-user-facing-text` explains.
4. Run `pnpm lint` and `pnpm test`, and try the card yourself in light and dark mode and on a phone. Add screenshots or a short video to the pull request: the frontend template asks for them.

A custom card in your own repository has no skills to load. The [custom card guide](/frontend/custom-ui/card/) is the reference there.

### Write documentation on home-assistant.io

The instructions of home-assistant.io tell agents to load the matching skill before they edit, and to load all that apply:

- `home-assistant-docs-writing-style` for any prose.
- `home-assistant-markdown-liquid-style` for links, images, Liquid, and other site syntax.
- `home-assistant-yaml-style` for YAML examples.
- `document-integration-docs` for an integration page. It takes the domain, like `/document-integration-docs <domain>` in Claude Code, and reads the triggers, conditions, and actions of the integration in core when you have core and the frontend cloned next to the documentation.

Two rules in those instructions matter most for AI work. Agents must not invent new dashboard, card, automation, or script examples unless you ask for them. And `document-integration-docs` must not trust the issue text or the existing docs unless core confirms them. Hold your own review to the same standard: check every option, default, and step against the code, and look at your page in the Deploy Preview. [Writing docs](/writing/) has the rest.

### Translations are not an AI task

Translations of the interface happen in [Lokalise](/glossary/lokalise/), by people. The [translation rules](/translate/reference/rules/) ask you to translate only into your native language, because machine translation shows. The agent instructions of the apps agree from the other side: an agent adds or changes English strings only. The Android skills say the translated files come from Lokalise and must never be added or edited, and the iOS skill says to only change the English `.strings` files.

There is one documented exception. For [voice intents](/translate/voice/style-guide/#drafts-from-an-ai-model), the [intents repository](https://github.com/OHF-Voice/intents) can generate a prompt that you paste into an AI model to draft the sentences of an intent. That is a draft, for a native speaker to rewrite.

## What to check yourself, every time

A tool's output is a draft. These are the checks that catch the mistakes that reviews of this very site found again and again.

- **Verify against the code, on the right branch.** The truth is the default branch of the repository, like `dev` for core and the frontend. Not your memory, not the tool's memory, and not a local clone that is weeks old. Function names, parameters, and commands change.
- **Claims about people, processes, and numbers need a source.** Who decides, who reviews, how long it takes, how many there are. No code proves these, and tools fill the gap with something that sounds right. Find an official page, or leave it out.
- **Watch the absolute words.** "Always", "never", "every", "only". Look for the exception: a second code path, a fallback, a feature flag. A condition often gets lost when a tool summarizes.
- **Test across lifecycle boundaries.** Code that works on the happy path breaks on the first update, on unload and reload, after a migration, when a device disappears and comes back, or with an empty list. Ask yourself what happens at each one.
- **Run the steps, in order, from a fresh start.** Instructions written by a tool often skip a `cd`, an install, or a setting that a later step needs.
- **Don't let a summary stand in for the source.** A tool that fetches a page or a file gives you its summary, and summaries garble names and numbers. Read the source yourself before you rely on a detail.
- **Read the diff before you commit.** Look for changes you didn't ask for, comments that promise more than the code does, and code you can't explain.
