# Home Assistant Contributors

The source of [contributors.home-assistant.io](https://contributors.home-assistant.io): everything you need to contribute to Home Assistant, whether you write code, design, write documentation, translate, moderate, or run releases.

This README is the guide for maintainers: what lives where, every script, and how to update the parts that come from elsewhere. Want to fix or add a page? Start with [Improve this contributor site](https://contributors.home-assistant.io/writing/this-site/). The writing rules for pages are in [`.github/copilot-instructions.md`](.github/copilot-instructions.md) (also linked as `AGENTS.md` and `CLAUDE.md`).

## Getting started

You need Node.js 24 (see `.node-version`) and pnpm (the version is in `packageManager` in `package.json`, Corepack picks it up).

```shell
pnpm install
pnpm dev
```

Search only works on a build, because Pagefind creates the index after it:

```shell
pnpm build
pnpm preview
```

Before you open a pull request:

```shell
pnpm check
pnpm build
pnpm links
pnpm structure
```

CI (`.github/workflows/ci.yml`) runs the same on every pull request. Netlify deploys the site; CI does not.

## Scripts

| Script | What it does | When to run it |
| --- | --- | --- |
| `pnpm dev` | Fetches the referrer list, writes the redirects, and starts the development server. | While you work. |
| `pnpm build` | The same, then builds the site to `dist/` and the search index. | To try search, and before `pnpm links`. |
| `pnpm preview` | Serves `dist/`. | After a build. |
| `pnpm check` | Type-checks the site and the front matter of every page. | Before every pull request. CI runs it. |
| `pnpm links` | Checks every link and anchor in `dist/`, every redirect, every anchor mapping, the share card and the Markdown version of every page, and the links in the files for agents. | After a build. CI runs it. |
| `pnpm structure` | Checks that every area has the expected skeleton. | When you add an area or move pages. CI runs it. |
| `pnpm clean` | Removes `dist/` and every cache of Astro. | When something looks stale and you do not know why. |
| `pnpm redirects` | Writes `public/_redirects` and `public/redirect-fragments.json` from `redirects/`. | The build does it. Run it by hand to inspect the output. |
| `pnpm fragments` | Maps old heading anchors to new headings, in `redirects/fragments.tsv`. | After renaming headings that old links point to. Needs a build. |
| `pnpm bashio` | Generates the Bashio reference in `src/content/docs/apps/bashio/`. | When Bashio changes, or after editing `scripts/bashio/`. |
| `pnpm symbols` | Generates the indexes of code symbols in `src/data/symbols/` from a core and a frontend checkout, measures the coverage, and reports mentions that no longer match. Needs Python. | After mentioning a new class, function, or module of core or the frontend on a page. A workflow runs it weekly. |
| `pnpm source-paths` | Checks which repository paths the docs mention exist, writes `src/data/source-paths.json`, and reports the ones that moved or are gone. Needs the `gh` CLI, or local checkouts. | After mentioning a new file of a repository on a page. |
| `pnpm tokens` | Syncs the design tokens from the frontend into `src/styles/tokens.css`. | When the frontend tokens change. |
| `pnpm components` | Bundles frontend components for the demos into `public/components/` and `public/static/`. | When updating the demos. Slow. |
| `pnpm check:demos` | Type-checks `demo-runtime/` against a frontend checkout. | After changing `demo-runtime/`. |
| `pnpm check:component-docs` | Compares the "In code" sections of the component pages with the frontend source. | Before and after editing a component page. A workflow runs it weekly. |
| `pnpm referrers` | Fetches the allowed referrers of the analytics. | The build does it. |
| `pnpm avatars` | Downloads the GitHub avatars of blog authors that are missing. | After adding an author. |

## Areas and pages

### Add a page

Add a Markdown file to the folder of its area, with a `title` and a `description`. Use `.mdx` only when the page needs a component, like a demo. Run `pnpm dev`, and the page is in the sidebar. The authoring rules explain `order`, `sidebarLabel`, sidebar groups, and the rest.

### Add an area

1. Add the area to `src/data/areas.ts`. The order there is the order on the homepage.
2. Create `src/content/docs/<id>/`, with `index.md` and `first-contribution.md` (order 1, `sidebarLabel: Your first contribution`).
3. If the area is reference only, like Architecture and Glossary, add it to `NO_FIRST_CONTRIBUTION` in `scripts/check-structure.mjs` instead of writing a first contribution.
4. Add an `"area: <id>"` rule to `.github/labeler.yml` and a label to `.github/labels.yml`, and create that label on GitHub.
5. Run `pnpm structure`. It fails when a step above is missing.

### Move a page

Add a row to the redirect map of its area in `redirects/` (see below), and fix the links to it. `pnpm links` finds the ones you missed.

### Daily build

The [events page](https://contributors.home-assistant.io/community/reference/events/) and the homepage show the upcoming events of the contributor community. The build reads them from public calendar feeds: the developers Google Calendar, and the Home Assistant Meetups and Community Day calendars on Luma. The feeds are listed in `FEEDS` in `src/lib/events.ts`, so a new Community Day calendar is one line there. The events only change when the site builds. `workflows/daily-build.yml` starts a build once a day.

To set it up:

1. In the Netlify settings of the project, under **Build hooks**, add a build hook for the `main` branch.
2. In GitHub, under **Settings** > **Secrets and variables** > **Actions**, add a repository secret named `NETLIFY_BUILD_HOOK` with the URL of the hook.

Without the secret, the workflow starts no build, and says so in a warning. When the feed can't be read, the build still passes: the pages show the subscribe links and a line that the calendar couldn't be loaded. A local build or `pnpm dev` keeps the feed for an hour in `node_modules/.cache/events/`.

### Page feedback

Every docs page ends with "Was this page helpful?" (`src/components/PageFeedback.astro`). A vote sends the Plausible custom events `Page helpful` or `Page not helpful`, the same ones home-assistant.io sends, and shows up on the [dashboard](https://plausible.openhomefoundation.org/contributors.home-assistant.io) once the goals are added there. "Give feedback" opens the feedback form with the page URL filled in, and "View feedback" searches the open issues that mention the page.

## Caches

Astro keeps rendered pages in `node_modules/.astro/` between builds, and only renders a page again when the page changes. Four things change pages without touching them, and all are handled:

- Glossary `autolink` words. The Markdown plugin carries a fingerprint of all words in the Astro config. When the words change, Astro sees a new config and renders everything again. In `pnpm dev`, the server restarts when the words change. Editing only the text of a term restarts nothing.
- The indexes of code symbols. The code symbols plugin carries a fingerprint of `src/data/symbols/core.json`, `frontend.json`, and of the element tags of the component pages the same way, so a new index renders every page again. In `pnpm dev`, the server restarts when an index changes.
- The index of source paths, `src/data/source-paths.json`. The plugin carries a fingerprint of it the same way, and `pnpm dev` restarts when it changes.
- Settings in `astro.config.mjs`. Astro handles those itself.

The share cards are cached in `node_modules/.cache/og/`, see [Share cards](#share-cards).

Netlify and CI start without a cache. When a page still looks stale, run `pnpm clean`.

## Share cards

Every page has a share card: the 1200 by 630 image that Slack, Discord, the forum, and social networks show in a link preview. The build makes one PNG per page, at `/og/<path of the page>.png`, and `src/layouts/Base.astro` points the `og:image` and `twitter:image` tags at it.

- `src/lib/og.ts` decides what is on a card: the area label, title, and description of a docs page, the byline of a blog post, and the cards of the homepage and the blog, and the default card for everything else, like the 404 page.
- `src/lib/og-render.ts` decides how a card looks. [Satori](https://github.com/vercel/satori) lays it out from a tree of elements with inline CSS (flexbox only, no stylesheets), resvg turns it into a PNG. Cards over 100 KB, like the gradient of the homepage card, go down to 256 colors with sharp. Figtree comes from `@fontsource/figtree`, because Satori cannot read WOFF2.
- `src/pages/og/[...slug].png.ts` lists every card and renders it.

To change the design, edit `src/lib/og-render.ts`, run `pnpm dev`, and open a card in the browser, like `http://localhost:4321/og/design/components/badge.png`. Check a long title too: titles stop after three lines, descriptions after two.

Rendering all cards takes about half a minute. Each PNG is cached in `node_modules/.cache/og/`, by a hash of everything on the card and the versions of the renderer, so the next build only renders the cards that changed. Delete the folder to render everything again; `pnpm clean` leaves it alone. CI keeps the folder between runs too.

## Files for agents

Language models and agents read the site as Markdown, following the [llms.txt proposal](https://llmstxt.org/). The build makes, from the collections and `src/data/areas.ts`:

- `/llms.txt`: the index of the site. Every area with its pages, or only its starting points when the area has more pages than `LARGE_AREA` in `src/lib/llms.ts`. The glossary and the blog are under "Optional".
- `/<area>/llms.txt`: every page of one area, in the order of the sidebar.
- `/llms-full.txt` and `/<area>/llms-full.txt`: the full text of every page, of the site or of one area.
- `<page URL>index.md`: the Markdown version of every docs page, like `/core/integrations/config-flow/index.md`. The HTML page points to it with `<link rel="alternate" type="text/markdown">`.

`src/lib/markdown-export.ts` turns the source of a page into its Markdown version. Imports go, links become absolute URLs, and components become text: a demo becomes a note with its markup, a diagram a nested list. A new component in an MDX page fails the build until it has a Markdown version there. `src/lib/llms.ts` writes the `llms.txt` files.

`public/robots.txt` points to `/llms.txt`. `pnpm links` checks that every docs page has its Markdown version, and every link in these files. Search and the sitemap leave them out.

## Redirects

The site replaced developers.home-assistant.io, data.home-assistant.io, and design.home-assistant.io. Their old URLs redirect here.

- `redirects/<area>.tsv`: one tab-separated row per old path, and the path that replaced it. Paths of developers.home-assistant.io start with `/docs/`, paths of the data site with `data.home-assistant.io/`. Lines starting with `#` are comments.
- `redirects/overrides.tsv`: wins when two maps disagree.
- `redirects/fragments.tsv`: old heading anchors on redirected pages, and the heading they became. Generated by `pnpm fragments`, reviewed by hand.
- `src/data/design-redirects.json`: the old design site used hash routes, which a server cannot see. A script on `/design/` uses this map.

`pnpm build` runs `pnpm redirects`, which turns the maps into `public/_redirects` (the Netlify format) and `public/redirect-fragments.json`. Both are ignored by Git: never edit them.

To update the anchor map after headings changed on redirected pages:

```shell
pnpm build
pnpm fragments
```

It needs checkouts of [developers.home-assistant](https://github.com/home-assistant/developers.home-assistant) and [data.home-assistant](https://github.com/home-assistant/data.home-assistant) next to this repository, or pass `--developers` and `--data`. It reads the old pages from `origin/master`, keeps rows that are already in the file, adds new guesses, and drops rows whose heading is gone. Review the new rows: a guess can be wrong. Set the new anchor to `-` for an old heading without a counterpart.

## The Bashio reference

The function lists of the [Bashio pages](https://contributors.home-assistant.io/apps/bashio/) come from the docblocks in the source of [Bashio](https://github.com/hassio-addons/bashio). The text above the lists, and which modules go on which page, is in `scripts/bashio/<page>.md`. The overview, `src/content/docs/apps/bashio/index.md`, is written by hand.

```shell
pnpm bashio                   # the main branch, from GitHub
pnpm bashio --ref some-tag    # another branch, tag, or commit
pnpm bashio --from ../bashio  # a local checkout
```

The script fails when Bashio has a module that no template lists, so new functions are never left out silently. Add the module to a template, run it again, and review the diff.

## Code symbols

When a page mentions code in inline code, like `HomeAssistant`, `homeassistant.components.fan`, or `SubscribeMixin`, the first mention becomes a link to its source on GitHub. Pointing at it, or tabbing to it, shows a card with what it is, where it lives, its signature, and the first sentence of its documentation. The link works without the card: the card is extra.

There is an index per repository, and a page uses one, by its area:

| Index | Areas | What it holds |
| --- | --- | --- |
| `src/data/symbols/core.json` | Core, Architecture, Security, Apps, and the glossary terms outside the Frontend group | Classes, functions, and methods of core, its modules, and the integration hooks |
| `src/data/symbols/frontend.json` | Frontend, Design, and the glossary terms in the Frontend group | Functions, classes, mixins, contexts, interfaces, types, and enums of the frontend |

So `hass` on a Core page is the Python object, and on a Frontend page the TypeScript one. Other areas, like the OS, link nothing: `CoreState` there is the one of the Supervisor. Never in the blog, code blocks, headings, or links.

What each generator reads:

- **Core**: `scripts/symbols/core.mjs` reads core with Git, and `scripts/symbols/extract.py` parses it with Python's own parser. It reads `core.py`, `core_config.py`, `config_entries.py`, `data_entry_flow.py`, `exceptions.py`, `setup.py`, the classes and type aliases in `const.py`, all of `helpers/` and `util/`, the entity base classes in `components/<entity platform>/__init__.py` and `entity.py` and the classes in their `const.py`, and `tests/common.py`. Also the rest of every entity platform, of `auth/`, and of the components at least three other integrations import from, like `bluetooth` or `conversation`: their methods only link qualified. And every module, for its docstring, when a page names it.
- **Integration hooks**: the functions your integration implements and core calls, like `async_setup_entry` or `async_step_user`, are in `scripts/symbols/hooks.json`, written by hand. Each links to the page here that explains it, and its card shows the signature, quoted from that page or from core. `pnpm symbols` checks that every quote is still in its file. Only the config flow steps listed there link: another step name is the one of your own flow.
- **Frontend**: `scripts/symbols/frontend.mjs` reads every TypeScript file in `src/` of the frontend with Git, and parses it with the TypeScript compiler of this repository. Custom elements, like `ha-button`, are not symbols: their API is on the component pages of the Design area. On Frontend and Design pages, the tag of an element that has a component page links to that page instead, unless the page already links there.

Each index keeps only what a page links to, so it stays reviewable. Links point at the commit in the index, with the line number. Signatures are stored formatted, the way Ruff formats Python and Prettier formats the frontend, with lines of about 60 characters. `src/lib/symbol-cards.ts` highlights them with Shiki when the site is built, and serves them at `/symbols/core.json` and `/symbols/frontend.json`.

`src/lib/code-symbols.mjs` decides what links, and the generators use the same rules. A wrong card is worse than none, so a mention only links when it can mean one thing:

- The inline code is exactly a name, `Name()`, a qualified name like `core.HomeAssistant`, `hass.bus.async_fire`, or `hass.callWS`, a member of an enum like `SensorDeviceClass.TEMPERATURE`, a module of core like `homeassistant.const`, or an import of one, like `from homeassistant.components.fan import FanEntity`.
- A bare name links only when it is defined once, it is not a plain word like `state` or `Supervisor`, not a name every integration defines like `async_setup_entry` (that one is a hook), and not the name of an attribute, like `entity_id`, or of an element property, like `narrow`.
- Methods of an entity platform, like `open_cover`, only link by their bare name on the page of that platform. There, the method of that platform wins, so `turn_on` on the climate page is the one of the climate entity.

```shell
pnpm symbols                                 # both, origin/dev of ../core and ../frontend
pnpm symbols --ref some-branch               # both, another branch, tag, or commit
pnpm symbols core                            # only core
pnpm symbols frontend --from /path/frontend  # only the frontend, another checkout
```

It needs a core and a frontend checkout next to this repository (run `git fetch` in them first), and the Python version core needs, from `.python-version` in core. The report lists, per index, the mentions that linked with the old index and match nothing now: the symbol was renamed, moved, or removed, so check the page. A missing symbol never fails the build. The mention just stays plain inline code.

### Coverage

`pnpm symbols` also writes `src/data/symbols/coverage.json`, and prints it: per area, how many inline code spans look like a code symbol, and how many of them link. And every mention that links to nothing, with how often and on which pages. The weekly pull request lists the new ones.

"Looks like a code symbol" is a guess, in `scripts/symbols/coverage.mjs`: CamelCase names, names followed by `()`, paths that start with `homeassistant.`, `hass.`, or `this.`, contexts and mixins, and anything that links. It leaves out YAML keys and options, state values, CSS properties, element tags, built-ins of Python and the browser, example names like `MyEntity`, intent names like `HassTurnOn`, and methods of a variable, like `response.as_dict()`.

An unresolved mention is one of these:

- A symbol the index does not read yet: widen what the generator reads, if it is public API of that repository.
- A name that is ambiguous, like `setConfig()`, which every card, badge, and row has: qualify it on the page, like `LovelaceCard.setConfig`, or leave it.
- A typo or an outdated name: fix the page.
- Code of another project, like `ClientSession` of aiohttp or `BleakClient`: it stays plain.

Mention a new class, function, or module on a page, and it links after the next `pnpm symbols`: run it in your pull request, or let the weekly workflow pick it up. Rules that need a new exception go in `src/lib/code-symbols.mjs`, with the evidence in a comment.

## Source paths

When a page mentions a file or a folder of a project repository in inline code, like `src/dialogs/more-info/controls/more-info-cover.ts` on a Design page, it links to that file on GitHub. Folders, like `homeassistant/helpers/`, link to the folder. The links point at the default branch, not a commit: they keep working when the file changes, and only break when it moves.

- `src/lib/source-paths.mjs` decides what links. `SCOPES` lists the repositories each folder of the docs is about: Core pages are about core (and `src/` of the frontend, `source/` of home-assistant.io, the brands), Design and Frontend pages about the frontend, and so on. A path only links when it exists in exactly one of them. A path in two, like `tests/` on an OS page that covers the Supervisor and the operating system, stays plain.
- Only inline code that is exactly a relative path, with a file extension or a trailing `/`. Not `/config/configuration.yaml`, `custom_components/<domain>/`, or a URL. Never in code blocks, headings, or links, so a code symbol keeps its own link.
- `NOT_REPOSITORY_PATHS` lists paths that look like a file of the repository and are not: a file you create yourself, or the example integration of a tutorial.
- `scripts/generate-source-paths.mjs` collects the paths the docs mention, reads the file trees of the repositories, and writes `src/data/source-paths.json`: the paths that exist, with their repository, branch, and whether it is a file or a folder.

```shell
pnpm source-paths                       # all from GitHub, with gh
pnpm source-paths --from core=../core   # core from a checkout
pnpm source-paths --from core=../core --from frontend=../frontend
```

The report lists the paths that are missing: the first folder exists in a repository of the page, the rest does not, or the path linked before. The file moved or is gone, so fix the page. They are in `missing` in the index too, with their pages. A missing path never fails the build, it just stays plain inline code.

A local checkout is read at `origin/<default branch>`, so run `git fetch` in it first. Mention a new file on a page, and it links after the next `pnpm source-paths`.

## Live demos

The Design area shows real frontend components, bundled from the [frontend](https://github.com/home-assistant/frontend) source. The bundle is committed, so building the site never needs the frontend.

- `scripts/build-components.mjs` lists the components to bundle (`COMPONENTS` and `EXTRA_ELEMENTS`).
- `public/components/loader.js` loads the components a page uses, when a demo comes near the viewport.
- `public/components/manifest.json` records the frontend commit, the translations artifact, and the date of the bundle.
- `demo-runtime/` has the fake Home Assistant (`ha-demo-hass.ts`), the fake home (`demo-home.ts`), and wrappers like `ha-demo-more-info.ts`. It imports the frontend as `frontend/...`.

### Update the demos to a new frontend

1. Get the frontend next to this repository, and install its dependencies:

   ```shell
   git -C ../frontend fetch
   git -C ../frontend checkout origin/dev
   pnpm --dir ../frontend install
   ```

2. Check that the demo runtime and the build patches still fit, without building anything:

   ```shell
   pnpm components --check
   ```

   Fix type errors in `demo-runtime/`. A patch that no longer matches means the frontend changed the code it patches: update `PATCHES` in `scripts/build-components.mjs`.

3. Log in to the GitHub CLI (`gh auth login`), or set `GITHUB_TOKEN`. Without a token, demos have the frontend strings, but no translations of integrations.

4. Build:

   ```shell
   pnpm components
   ```

   Pick another commit with `--ref`, or another checkout with `--from`. The script builds in temporary folders, and only replaces `public/components/` and `public/static/` when everything worked. A failed run leaves the old demos in place.

5. Run `pnpm dev`, and look at the pages with demos. `pnpm build` and `pnpm links` must still pass.

6. Commit `public/components/`, `public/static/`, and any change to `demo-runtime/` together.

To add a component, add it to `COMPONENTS` in `scripts/build-components.mjs`, run `pnpm components`, and use it in a `<Demo>`. Components that need Home Assistant go in `<Demo hass>`. When a demo needs a device or entity the fake home does not have, add it to `demo-runtime/demo-home.ts`.

### The weekly rebuild

Every Monday, `.github/workflows/update-demos.yml` does steps 1 to 4 above on the frontend `dev` branch, and runs `pnpm build` and `pnpm links`. When the demos changed, it opens a pull request labeled `demos`, with the frontend commit in the title. The next week, it updates the same pull request. When only the date in the manifest changed, there is no pull request. You can also start it by hand, under **Actions** > **Update demos** > **Run workflow**.

What the workflow can't do is look at the demos. Before you merge, check the pages with demos in the browser, like step 5 says.

The workflow needs some repository settings:

- Under **Settings** > **Actions** > **General**, **Allow GitHub Actions to create and approve pull requests** must be on. Without it, the build works, and opening the pull request fails.
- A pull request opened with the token of a workflow does not start other workflows, so CI does not run on it. Close and reopen the pull request to start CI. To have CI start by itself, give the workflow the token of a GitHub App instead.
- The translations of integrations come from an artifact of the frontend's nightly workflow, downloaded with the token of the workflow. If that download fails, the build fails, instead of leaving the translations out. Should the token of the workflow ever not be enough to read artifacts of the frontend repository, pass a token that can (a fine-grained token with read access to public repositories) as `GITHUB_TOKEN` in the "Build the demos" step.

The job that installs and runs the frontend only has read access. A second job, which runs nothing from the frontend, pushes the branch and opens the pull request.

### The written reference drifts

The demos are built from the frontend, so they are current after every rebuild. The "In code" sections of the component pages are written by hand: when the frontend renames an attribute, the page keeps the old name until someone notices.

`pnpm check:component-docs` notices. For every page in `src/content/docs/design/components/`, it reads the frontend files the page links as its source, from `origin/dev` of `../frontend`, and collects the attributes, properties, slots, events, CSS custom properties, and methods. Then it compares those with the lists under "In code", per element, and reports:

- **Documented, but not in the source**: probably renamed or removed. Fix the page. With `--strict`, the check fails on these.
- **Linked or documented, but gone from the source**: a source file the page links, or an element it documents, no longer exists. Fix the page. With `--strict`, the check fails on these too.
- **Not in the frontend code, may come from the package**: the component extends or wraps a Web Awesome or Material component, and the name may come from there. The check does not read packages: check these by hand when you edit the page.
- **In the source, but not documented**: maybe on purpose, maybe forgotten.

```shell
git -C ../frontend fetch
pnpm check:component-docs                        # origin/dev of ../frontend
pnpm check:component-docs --ref some-branch      # another branch, tag, or commit
pnpm check:component-docs --json report.json     # also write the report as JSON
pnpm check:component-docs --strict               # fail on what is missing or gone
```

It only reads the frontend with Git, so it needs no installed dependencies. It reads what a page documents from the lists under the **Attributes**, **Properties**, **Slots**, **Events**, **Styling**, and **Methods** headings, or the same words as a lead-in, like "Attributes:". Keep to that shape, or the check can't see what a page documents. The [`design-component-page` skill](.github/skills/design-component-page/SKILL.md) describes it.

Every Monday, `.github/workflows/component-docs-drift.yml` runs the check against the frontend `dev` branch, and keeps one issue labeled `area: design` up to date. It opens the issue when something documented is missing or gone, edits it while that stays so, and closes it when the pages match again.

## Skills and review instructions

Everything learned while building this site lives in the repository, so the next author, person or agent, does not repeat the same mistakes.

- [`.github/copilot-instructions.md`](.github/copilot-instructions.md): the rules. `AGENTS.md` and `CLAUDE.md` link to it.
- [`.github/instructions/`](.github/instructions/): short checklists for Copilot code review. `review-content.instructions.md` applies to `src/content/`, `review-site.instructions.md` to the site code.
- [`.github/skills/`](.github/skills/): step-by-step workflows. `.claude/skills` links to this folder, so Copilot and Claude Code read the same files.

| Skill | Use it to |
| --- | --- |
| `review` | Review a pull request, pages, or site code in depth, and report findings with evidence. |
| `write-page` | Add or change a page. |

## Design tokens

Colors, spacing, and typography come from the Home Assistant frontend. `src/styles/tokens.css` is generated, do not edit it by hand:

```shell
pnpm tokens                     # from the dev branch on GitHub
pnpm tokens --from ../frontend  # from a local checkout
```

Components use the `--site-*` aliases from `src/styles/global.css` where one exists (colors, fonts, and the radius of cards and tiles), not the raw `--ha-*` tokens. Spacing, other radii, and shadows have no alias: use `--ha-space-*`, `--ha-border-radius-*`, and `--ha-box-shadow-*` directly.
